微前端 ​

什么是微前端 ​

微前端（Micro Frontends）架构可以被理解为“前端领域的微服务”。它的核心思想是：将一个庞大、复杂的单体前端应用 拆分为多个独立开发、独立测试、独立部署的小型前端应用，最后通过一个“容器应用”（Main/Host App）将它们集成在一 起展示给用户。

微前端解决的问题 ​

微前端方案主要是为了解决传统单体前端（Monolithic Frontend）在复杂应用中存在的问题。

  1. 技术栈隔离：

    单体应用一旦选定 React 或 Vue，后续所有模块都必须跟随。微前端允许不同子应用使用不同的技术栈（React, Vue, Angular 甚至原生 JS）。

  2. 代码解耦和风险隔离：

    在单体应用中，修改一个角落的全局样式或变量，可能导致另一个模块崩溃。微前端通过**沙箱隔离（Sandbox）**实现了逻辑和样式的物理/逻辑隔离。这种隔离使得 一个微应用的故障不会影响整个系统，提高了系统的稳定性和可靠性。

  3. 发布流水线拥堵：

    单体应用哪怕只改一个错别字，也要全量编译发布，耗时长且风险高。微前端支持独立发布，子应用上线无需通知主应用。

  4. 团队协作：

    对于庞大的单体应用，代码的合并、构建、测试对于团队来讲都是灾难。微前端让团队可以按业务功能横向拆分，每个团队负责自己的子应用。

微前端的主要优势 ​
  1. 技术无关性：每个团队可以选择最适合业务场景的工具。
  2. 快速增量升级：可以在不重构整个应用的情况下，用新技术开发新功能，或者逐步替换旧模块（如：主应用 React，新功能用 Vue 3）。
  3. 独立开发与部署：每个子应用由独立团队负责，按照团队的节奏迭代、部署。
  4. 高复用性：子应用可以像组件一样，被集成到不同的业务系统中。
  5. 强隔离性：一个子应用崩溃不会导致整个门户挂掉，容错性更高。
微前端的应用场景 ​

虽然微前端很强大，但它也带来了首屏加载慢（多次资源请求）和管理复杂度增加的问题。因此，它通常适用于以下场景：

  1. 超大型项目：由不同的团队开发、共同构建的应用，如企业级的 ERP、CRM、工业软件解决方案等。
  2. 老项目重构：使用新技术去开发新功能，而旧项目又不能直接扔掉，可以使用微前端进行“渐进式”迁移。

综上所述：微前端并不是“让应用跑得更快”的技术，它是“让团队协作和代码维 护不随着应用规模扩大而崩盘”的架构方案。如果你的项目只有几个人维护，业务简单，强行上微前端只会增加“架构负担”。

微前端框架需要具备的能力 ​

微前端架构中的核心：如何让多个独立运行的应用在同一个浏览器页面里“互不干扰”地和平共处。

  • JS 隔离
  • 样式隔离
  • 路由同步
  • 状态管理

样式隔离的实现方式 ​

如果子应用 A 定义了 .title { color: red; }，而子应用 B 也有一个 .title 且希望它是蓝色的，后加载的样式就会覆盖掉先加载的。

常见的解决方案：

  1. Shadow DOM (最硬核的隔离)：

    利用浏览器原生的 Shadow DOM API，将子应用挂载在 Shadow Root 下。这样 CSS 永远不会逃逸出这个容器。 缺点： 由于绝大多数 UI 组件库会把弹窗挂载到 body 下， 而 shadow DOM 内部 CSS 无法影响到外部样式，导致挂载位置出错。

JS 隔离的实现方式 ​

实现 JS 隔离有下面两种方案，但是各自都存在着需要解决的问题。

  • iframe 实现 JS 隔离。

  • 纯手工实现 JS 沙箱。纯手工实现 JS 沙箱需要解决的问题：

    1. 共享上下文环境。主应用和子应用共享上下文环境，访问的是同一个 window、globalThis。

    2. 全局数据泛滥。JS 框架或者代码里存在大量显性 + 隐性读写全局。

    3. 读写冲突。

      • 禁止写：子应用修改全局变量时必须隔离，不能修改真实全局，否则会互相覆盖。
      • 不能禁读：子应用必须能正常使用全局变量，如 document、location。

    4. 全局副作用的清理。

      子应用运行期间在全局产生的大量“环境垃圾”需要清理，否则会拖垮主应用。

微前端方案：qiankun（乾坤） ​

qiankun 是基于 single-spa 进行的深度二次封装，解决了 single-spa 过于底层、无沙箱机制、需要手动处理资源加载的痛点。

核心原理 ​

qiankun 是基于两个关键库构建的：

  1. single-spa：负责路由匹配、应用状态切换。
  2. import-html-entry：负责 HTML、JS、CSS 资源的加载、处理。

在此基础上，qiankun 补全了微前端最核心的两个能力：沙箱隔离、应用间通信。

JS 沙箱隔离 ​

qiankun 使用 ProxySandbox （多例沙箱） 实现子应用 JS 的隔离：即它会为每一个子应用都创建一个 ProxySandbox 实例作为沙箱环境。

  • 沙箱创建
  • 多沙箱管理
沙箱原理 ​

多例沙箱利用了 ES6 的 Proxy 特性。它并不直接操作原生的 window 对象，而是为每个微应用创建一个 fakeWindow。

微前端方案：wujie（无界） ​

使用 ​

子应用注册 ​

wujie 注册子应用主要分为三个步骤：配置注册和渲染挂载、子应用配置。

第一步：配置注册

这一步通常在主应用的入口文件（如 main.js 或 main.ts）中进行。你需要使用 setupApp 或 preloadApp 来注册子应用的元数据。

  • setupApp：定义子应用的全局配置（如名称、地址、生命周期等）。
  • preloadApp：（可选）预加载子应用的静态资源，提升首屏速度。

下面示例是常规注册的方式：

js
import WujieVue from "wujie-vue3";

const { setupApp, preloadApp } = WujieVue;

// 1. 注册子应用配置
setupApp({
    name: "marketing", // 子应用唯一标识，必须与渲染时的 name 一致
    url: "//localhost:7600/", // 子应用的访问地址
    alive: true, // 是否开启保活模式（单例模式需设为 false）
    // 其他配置...
});

// 2. (可选) 预加载子应用
preloadApp({
    name: "marketing",
    url: "//localhost:7600/",
    exec: true, // 是否预执行（提前渲染），会占用线程但首屏更快
});

第二步：渲染挂载

配置好之后，你需要在具体的页面组件中使用 <WujieVue>（或 <WujieReact>）组件将子应用渲染出来。 关键点： 组件上的 name 属性必须与 setupApp 中注册的 name 完全一致，无界才能知道这里要显示哪个子应用。

vue
<template>
    <div class="main-layout">
        <!-- 侧边栏菜单 -->
        <Sidebar />

        <!-- 子应用容器 -->
        <div class="content">
            <WujieVue
                width="100%"
                height="100%"
                name="marketing"
                :props="propsData"
                :sync="true"
            />
        </div>
    </div>
</template>

<script setup>
import { ref } from "vue";
// 传递给子应用的数据
const propsData = ref({
    userInfo: { name: "Admin", id: 1001 },
    onLogout: () => {
        console.log("logout");
    },
});
</script>

第三步：子应用配置

注册不仅仅是主应用的事，子应用也需要做简单的配合：

  1. 开启跨域 (CORS)：

    由于无界是通过 fetch 获取子应用的 HTML，所以子应用的服务端必须允许跨域。

    • 响应头：Access-Control-Allow-Origin: *

  2. 生命周期改造 (仅限单例模式)：

    如果 alive: false（单例模式），子应用需要导出 __WUJIE_MOUNT 和 __WUJIE_UNMOUNT 生命周期钩子，以便无界控制子应用的挂载和卸载。如果是 alive: true（保活模式），通常不需要改造。

子应用动态注册 ​

在实际的企业级项目中，子应用可能非常多，且需要动态增删。这时通常不会把 setupApp 写死在代码里，而是通过接口获取配置。

逻辑流程：

  • 主应用启动时，请求后端接口获取“子应用列表配置”。
  • 遍历返回的列表，循环调用 setupApp 进行注册。
  • 动态渲染子应用。
js
// 从后端获取子应用配置
const appList = await fetch("/api/get-sub-apps");

appList.forEach((app) => {
    // 动态注册每一个子应用
    setupApp({
        name: app.name,
        url: app.entryUrl,
        // ...其他配置
    });
});

子应用加载 ​

wujie 决定加载哪个子应用，并不是像传统路由那样在框架内部维护一张静态的“路由表”，而是采用了一种“主应用驱动 + 动态匹配”的机制。

核心原理 ​

wujie 可以概括为一种“三位一体”的架构设计，它巧妙地将 iframe、Web Component 和 Proxy 三种浏览器原生技术结合起来，分别解决了微前端架构中的三大核心难题：JS 隔离、CSS 隔离 和 通信与路由。

其核心思想是：让子应用的 JS 代码在 iframe 的沙箱中运行，将其 DOM 结构渲染在 Web Component 的 Shadow DOM 中，并通过 Proxy 将两者无缝连接，同时利用它们天然的“同域”特性实现高效的通信和路由同步。

下面，我们将从这三个方面深入剖析其底层原理。

子应用加载过程 ​

隔离机制：JS 沙箱与 DOM 沙箱的分离 ​

wujie 的 JS 隔离并非单一技术，而是由两个紧密协作的沙箱共同构成：

  1. JS 执行沙箱 (iframe)

    子应用所有的 JS 代码，包括其依赖的库、业务逻辑等，都会被注入到一个同域的 iframe 中执行。iframe 为子应用提供了一个原生的、独立的 window、document 和 history 对象，从物理上保证了 JS 变量的隔离，子应用无法直接污染主应用的全局环境。

  2. DOM 操作沙箱 (Web Component)

    子应用的 DOM 结构并非渲染在 iframe 内部，而是被渲染在主应用页面中的一个自定义元素（如 <wujie-app>）的 Shadow DOM 里。这实现了 CSS 样式的天然隔离。

那么，运行在 iframe 里的 JS 代码是如何操作到 iframe 外面的 Shadow DOM 的呢？这就引出了最关键的一步——代理连接。

连接机制: Proxy 代理劫持 ​

无界通过 Proxy 对象，对 iframe 中的 window、document 等全局对象进行了深度代理。当子应用的代码尝试访问或修改这些对象时，实际上访问的是代理对象， 代理层会进行拦截，并将其操作重定向到正确的目标上。

  • window 对象代理：隔离全局变量，防止子应用修改 window 对象影响主应用。它的工作机制如下：

    1. 创建一个 proxyWindow 代理对象。
    2. 拦截 get 操作：当子应用读取 window.xxx 时，优先从子应用自己的沙箱作用域中查找，如果找不到，再返回 iframe 原生 window 对象的值。
    3. 拦截 set 操作：当子应用设置 window.xxx = yyy 时，这个属性会被存储在子应用自己的沙箱作用域中，而不会污染 iframe 或主应用的 window 对象。

  • document 对象代理 ：将子应用对 DOM 的所有查询和操作，全部劫持并重定向到主应用的 Shadow DOM 容器中。它的工作机制如下：

    1. 创建一个 proxyDocument 代理对象。
    2. 拦截 DOM 查询方法：当子应用调用 document.getElementById('app') 或 document.querySelector('.btn') 时，代理层会将查询范围限定在 Shadow DOM 内部。
    3. 拦截 DOM 操作方法：当子应用调用 document.createElement('div') 时，代理层会调用 Shadow DOM 所属的 document 来创建元素，确保创建出的元素属于正确的文档上下文。

下面我们通过伪代码说明一下这个代理机制。

js
// 伪代码：JS隔离核心逻辑
const iframe = document.createElement("iframe");
const shadowRoot = webComponent.attachShadow({ mode: "open" });

// 伪代码：window 对象代理
const sandboxScope = {}; // 子应用私有的全局变量存储区
const proxyWindow = new Proxy(iframe.contentWindow, {
    get(target, key) {
        // 1. 优先从子应用自己的沙箱作用域中获取
        if (key in sandboxScope) {
            return sandboxScope[key];
        }
        // 2. 否则，返回 iframe 原生 window 的值
        return target[key];
    },
    set(target, key, value) {
        // 将全局变量赋值操作，限制在子应用的沙箱作用域内
        sandboxScope[key] = value;
        return true;
    },
});

// 伪代码：document 对象代理
const proxyDocument = new Proxy(iframe.contentDocument, {
    get(target, key) {
        const originalValue = target[key];

        // 拦截 DOM 查询方法
        if (key === "getElementById") {
            return (id) => shadowRoot.getElementById(id);
        }
        if (key === "querySelector") {
            return (selector) => shadowRoot.querySelector(selector);
        }
        if (key === "querySelectorAll") {
            return (selector) => shadowRoot.querySelectorAll(selector);
        }

        // 拦截 DOM 创建方法
        if (key === "createElement") {
            return (tagName) => shadowRoot.ownerDocument.createElement(tagName);
        }

        // 其他属性或方法，返回原始值
        return typeof originalValue === "function"
            ? originalValue.bind(target)
            : originalValue;
    },
});

通过这两层代理，无界成功地将子应用的 JS 执行环境和 DOM 操作环境解耦并重新连接。子应用代码感觉自己运行在一个完整的浏览器环境中，但实际上它的 JS 变量被限制在 iframe 内，而它的 DOM 操作则被精确地控制在主应用的 Shadow DOM 里，从而实现了强大而高效的 JS 隔离。

路由同步 ​

在正常情况下，子应用 iframe URL 与主应用 URL 是完全隔离且不一致的。这也是为什么传统 iframe 方案被诟病：刷新页面后，iframe 内部的路由会重置回初始状态，且主应用无法感知子应用当前的 URL。

wujie 的路由机制核心在于双向同步。它通过一种巧妙的设计，使得主应用和子应用的路由状态能够保持一致，无论是浏览器的前进/后退操作，还是通过代码触发的路由跳转，都能在主、子应用间同步。
