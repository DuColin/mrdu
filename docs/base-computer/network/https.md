# HTTPS

总的来讲，HTTPS 并不是开发了一套全新协议，而是在应用层和 HTTP 传输层之间，，加入了一个加密层（在早期叫 SSL，现在标准化后叫 TLS）。利用非对称加密交换密钥，利用对称加密传输数据和数字证书验证身份，从而确保了网络通信的机密性、完整性和真实性。

## 为什么要用 HTTPS ?

HTTP 协议因为是明文传输，在传输过程中会面临三大安全威胁：

- **窃听**：由于数据没有加密，第三方（比如公共 Wi-Fi 的黑客、不合规的运营商）可以轻易抓包截获你的账号密码。
- **篡改**： 中间人可以偷偷修改你传输的内容，比如著名的“运营商劫持”，经常在你访问的正常网页里强行弹小广告。
- **冒充**：你以为你访问的是淘宝，其实是黑客搭建的钓鱼网站，你根本无法确认对方的真实身份。

为了解决这三个痛点，HTTPS 应运而生。

## TLS 的核心功能

TLS 使用下面四种方式，确保 HTTP 数据传输过程的安全性。

1. **对称加密（负责：高效加密数据）**

    - 原理：通信双方使用**同一把密钥**来加密和解密数据。常用的算法有 AES、ChaCha20。
    - 优点：计算速度极快，性能消耗小。
    - 致命问题：密钥怎么安全地给到对方？如果在公网上直接发送这把密钥，一旦被黑客截获，后续的加密就形同虚设。

2. **非对称加密（负责：安全地传输密钥）**

    - 原理：拥有两把钥匙——公钥和私钥。
        - **公钥**是公开的，任何人都能拿去**加密**数据。
        - **私钥**是严格保密的，只有服务器自己有，用来**解密**由公钥加密的数据。
    - 优点：极为安全，不需要在网上拉扯“私钥”。
    - 缺点：计算极其复杂，非常消耗 CPU 性能，无法直接用来加密庞大的网页内容。


    HTTPS 的绝妙组合：用非对称加密来安全地传递“对称密钥”，一旦双方对好了对称密钥，后面所有的数据传输全部改用对称加密。

3. **数字证书与 CA 机构（负责：身份验证）**

    有了非对称加密，黑客依然可以玩“中间人攻击”：黑客拦截你的请求，把自己的公钥冒充服务器的公钥发给你。

    为了证明“公钥确实是真正服务器的”，就必须引入一个权威的第三方担保人——**CA 机构（证书颁发机构）**。

    - 服务器会向 CA 机构申请一张数字证书（Digital Certificate），证书里包含：服务器域名、服务器的公钥、证书到期时间等。
    - 浏览器只要信任 CA 机构（各大操作系统的浏览器内部都内置了根证书），就可以验证这张证书的真伪。只要证书合法，就能确保手里的公钥没被调包。

4. **摘要算法与数字签名（负责：防止内容篡改）**

    - 摘要算法（如 SHA-256）：把任意长度的内容，计算出一个固定长度的“哈希值”（也叫指纹）。内容只要变了一个标点符号，哈希值都会天差地别。
    - 数字签名：CA 机构将证书的内容用摘要算法算出哈希值，然后用 CA 自己的私钥对这个哈希值进行加密。这个加密后的密文就是“数字签名”。
    - 如何防篡改：浏览器收到证书后，用 CA 的公钥解密签名得到哈希值 $A$，再用同样的摘要算法计算证书内容的哈希值 $B$。如果 $A == B$，说明证书在传输过程中绝对没有被中间人篡改过。

## HTTPS 的握手全流程


###### 第一阶段：建立TCP连接

这个阶段是在加密通信开始前，客户端（你的浏览器）和服务器需要先通过“三次握手”建立一个基础的TCP网络连接。
 
##### 第二阶段：身份验证

这个阶段的目标是通过**CA（证书颁发机构）的数字签名**验证服务器的身份，防止“中间人攻击”（即黑客冒充目标网站）, 并且获取服务器的公钥。

1. **客户端发起请求 (Client Hello)**：浏览器向服务器发送一个随机数 `Random_C`，以及客户端支持的 TLS 版本和加密套件(如加密算法)列表。
2. **服务端回应 (Server Hello & Certificate)**：服务器从中选定一套加密算法，回复另一个随机数 `Random_S`，并且把自己的**数字证书**（包含服务器公钥）发送给浏览器。
3. **客户端验证证书**：浏览器使用操作系统/浏览器中内置的 CA（证书颁发机构）根证书公钥，解密证书上的数字签名。验证成功则说明该证书真实有效，里面的服务器公钥是真实可信的。

##### 第三阶段： 密钥交换

在这个阶段，客户端和服务端利用这个**已经确认可信的公钥/私钥对**（非对称加密），在不安全的网络上安全地计算和传递出一个**对称加密的密钥**（会话密钥）。


在实际应用中，非对称加密是如何“获取对称密钥”的，取决于服务器使用的算法。主要有两种主流方式：

- **方式一：RSA 算法（经典方式）**
    
    - **过程**：客户端在本地生成一个随机数（预主密钥），直接用服务端的公钥加密发过去，服务端用私钥解密。
    - **缺点**：缺乏“前向安全性”——如果服务器的私钥在几年后泄露了，黑客就能解密当年录下的所有历史流量。

- **方式二：DH / ECDHE 算法（现代主流，TLS 1.3 强制使用）**

    - **过程**： 客户端和服务端都不直接传输最终的密钥。

        1. 服务端生成一个临时参数，用自己的私钥签名（加密）发给客户端（证明身份）。
        2. 客户端用服务端公钥解密并验证签名，确认身份无误。
        3. 双方通过公开交换一组数学参数（通过复杂的离散对数或椭圆曲线算法），在各自的本地独立计算出完全相同的对称密钥。

    - **优点**：在这个过程中，服务端的公钥/私钥主要用来对参数进行签名和验证（身份验证），而对称密钥是通过数学算法“隔空”各自算出来的，即使黑客拦截了所有网络数据，也算不出这个密钥。这保证了即使未来私钥泄露，历史数据也绝对安全。


#### 第四阶段： 加密传输

-  **对称加密通信**：TLS 握手正式结束。接下来的所有 HTTP 请求和响应（如网页 HTML、图片、API 数据），客户端和服务端都只会用“会话密钥”进行对称加密和解密。黑客即使拦截了数据包，没有会话密钥也无法破解内容。
