#  HTTP


## http 版本 

http 从诞生到现在，经历了多个版本的演进。每一次升级都是为了解决当时网络环境下的痛点（比如延迟、带宽利用率、安全性等）。以下是 http 协议的主要版本及其核心特点：

1. **HTTP/0.9 (1991年)**
   
   这是 http 的初始原型版本，设计极其简单。

   - 只有一个 `GET` 请求方法，且没有请求头和响应头。
   - 响应体仅为纯 HTML 文本，不支持图片、视频等其他格式。
   - 采用短连接，即一次请求对应一次 TCP 连接，请求完成即断开。

   该版本目前早已退出历史舞台，仅作为协议演进的起点被提及。

2. **HTTP/1.0（1996年）**

   - 增加了 `POST`、`HEAD` 请求方法，并增加了 Header（请求头/响应头）。
   - 通过 `Content-Type` 支持了图片、视频、二进制文件等多种数据格式。
   - 引入了状态码（如 200 OK, 404 Not Found），让浏览器知道发生了什么。

3. **HTTP/1.1（1999年）**

   为了解决 1.0 的性能瓶颈，1.1 版本做出了重大改进。这是长期以来的主流版本，也是目前兼容性最强的版本。
   
   - 默认开启持久连接：`Connection: keep-alive`。同一个 TCP 连接可以发送多个请求，不用每次都重新握手。
   - 允许在同一个 TCP 连接上同时发送多个请求，但服务器必须**按顺序**响应。
   - 增加了 `PUT`、`DELETE`、`OPTIONS` 等请求方法。

   它的复用其实是“伪并行”：虽然连接复用了，但协议规定请求必须排队发送。所以存在下面的痛点：

   - 队头阻塞 (Head-of-Line Blocking)：如果前一个回应慢，后面的回应就得排队等着。为了加速，浏览器不得不对同一个域名开启多个 TCP 连接（通常上限为 6 个）。


4. **HTTP/2（2015年）**

   由 Google 的 SPDY 协议演进而来，核心目标是解决 1.1 的延迟和并发问题：

   - 二进制分帧 (Binary Framing)：不再使用纯文本，而是将数据分成了更小的“帧”并采用二进制编码，解析更高效。
   - 多路复用 (Multiplexing)：**彻底解决应用层队头阻塞**。在同一个 TCP 连接上，多个请求和响应可以交错并发，不用排队等待。
   - 头部压缩 (HPACK)：通信双方共同维护一张 Header 表，避免每次都发送重复的、臃肿的 Header（如 User-Agent），节省带宽。
   - 服务器推送 (Server Push)：服务器可以主动把客户端接下来可能需要的资源（如 CSS/JS）推送到浏览器缓存中。


   尽管 HTTP/2 的多路复用解决了“应用层”的排队问题，但它无法改变底层“TCP 协议”的传输规则：**保证字节流严格有序交付**。所以当网络丢包后，TCP 会一直等待数据包被重传并补齐。因为所有的 HTTP/2 请求（流）都挤在这唯一的一条 TCP 连接上，TCP 层的这种“等包”行为，就会引发连锁反应。

   这就会导致 HTTP/2 依然存在下面的问题：

   - 基于 TCP 协议。如果遇到网络丢包，TCP 的重传机制会导致整个 TCP 连接阻塞（传输层的队头阻塞）。
   
5. **HTTP/3（2022年）**

   为了解决 HTTP/2 在 TCP 传输层的队头阻塞问题，HTTP/3 做出了颠覆性的改变：

   - 基于 QUIC 协议：摒弃了 TCP，改用基于 UDP 的 QUIC 协议（Quick UDP Internet Connections）。
   - 彻底解决队头阻塞：QUIC 内部实现了独立的分流，某个连接丢包只会影响那一个流，其他流不受影响。
   - 极速建连：将传输层握手（UDP）和加密层握手（TLS 1.3）合二为一，最快可以实现 0-RTT 建立连接。
   - 连接迁移 (Connection Migration)：基于“连接 ID”而非 IP 地址标识用户。这意味着你从 Wi-Fi 切换到 5G 移动网络时，视频或下载不会中断。


## http 缓存


### 缓存机制

HTTP 的缓存机制是 Web 性能优化的核心手段，它的主要目的是减少网络请求次数、降低服务器压力并加速页面加载。

在 HTTP 中，缓存主要分为两大类：强缓存（Strong Cache）和协商缓存（Comparison Cache / Validation Cache）。浏览器在发起请求时，会先走强缓存，如果强缓存失效，才会触发协商缓存。


##### 强缓存（不向服务器发请求）

强缓存是指浏览器在请求某个资源时，先检查本地缓存。如果缓存没有过期，浏览器直接使用本地缓存中的资源，根本不会向服务器发送任何网络请求。在控制台中，你会看到状态码为 `200 OK (from disk cache)` 或 `200 OK (from memory cache)`。


强缓存主要通过以下两个响应头来实现：

1. **Expires**（HTTP/1.0 产物）

   - 原理：服务器返回一个绝对时间（如 Expires: Wed, 21 Oct 2026 07:28:00 GMT）。浏览器下次请求时，如果本地系统时间早于这个时间，就直接使用缓存。
   - 缺点：由于使用的是客户端的本地时间，如果用户手动修改了电脑的时钟，或者客户端与服务器存在时差，就会导致缓存判断失误。
 
2. **Cache-Control**（HTTP/1.1 产物，推荐）

   为了解决 `Expires` 的时间不准确问题，HTTP/1.1 引入了 `Cache-Control`，它使用的是相对时间，优先级高于 `Expires`。

   常用的指令有：

   - `max-age=3600`：表示资源在未来的 3600 秒内都是有效的。
   - `public`：表明响应可以被任何对象（包括发送请求的客户端、代理服务器、CDN 等）缓存。
   - `private`：表明响应只能被单个用户（浏览器）缓存，中间代理/CDN 不能缓存。
   - `no-cache`： **误区警告！** 它并不意味着“不缓存”，而是指每次使用缓存前，必须先去服务器进行协商缓存验证。
   - `no-store`：这才是真正的绝对不缓存，每次都必须重新从服务器下载。

##### 协商缓存（向服务器发请求验证）

当强缓存过期了，或者 `Cache-Control` 设置了 `no-cache` 时，浏览器就会携带缓存标记去向服务器询问：“我手里的这份资源还能用吗？”

服务器会验证这个资源是否有更新：
- 如果**没有更新**：服务器返回状态码 `304 Not Modified`，不携带具体数据，告诉浏览器继续用旧缓存。
- 如果**有更新**：服务器返回状态码 `200 OK`，并返回最新的资源。

协商缓存由两组头部实现，每次请求只能基于其中一对或两对组合配合使用：


1. **Last-Modified / If-Modified-Since（基于时间验证）**

   1. 首次请求：服务器返回资源的同时，在响应头加上 `Last-Modified`，记录该文件在服务器上的最后修改时间。
   2. 再次请求：强缓存失效后，浏览器把这个时间放在请求头的 `If-Modified-Since` 中发给服务器。
   3. 服务器判断：服务器比对文件最后修改时间。没变则返回 304，变了则返回 200 和新资源。

   基于时间的缓存机制，存在下面的缺点：
   - 如果文件内容没有发生变化，但最后修改时间改变了，就会导致缓存失效。
   - 精度只到秒级。如果文件在 1 秒内修改了多次，它无法识别；或者文件只是被打开保存了一下，内容没变，也会导致缓存失效。

2. **ETag / If-None-Match（基于内容哈希精确验证，优先）**

   1. 首次请求：服务器根据文件内容生成一个唯一哈希字符串，通过响应头 ETag 返回给浏览器。
   2. 再次请求：强缓存失效后，浏览器将该值放入请求头的 If-None-Match 中发给服务器。
   3. 服务器判断：服务器比对当前文件的哈希值。一致则返回 304，不一致则返回 200。

   只要文件内容变了，`ETag` 必定会变，判断极其精准。`ETag` 的优先级高于 `Last-Modified`。

### 缓存处理流程

浏览器在发起一个资源请求时的完整决策链条如下：

1. **检查强缓存：**

   - 检查 `Cache-Control`（或 `Expires`）。
   - 未过期 $\rightarrow$ 直接读取本地缓存，状态码 `200 (from cache)`。
   - 已过期 / 设置了 `no-cache` $\rightarrow$ 进入协商缓存。

2. **发起协商缓存：**

   - 浏览器在请求头中带上 `If-None-Match`（如果有 `ETag`）和 `If-Modified-Since`（如果有 `Last-Modified`）。

3. **服务器评估：**

   - 优先对比 `If-None-Match` 与服务器当前的 `ETag`。
   - 如果一致（或时间未变） $\rightarrow$ 返回 `304 Not Modified`，浏览器读取本地缓存。
   - 如果不一致（内容已变） $\rightarrow$ 返回 `200 OK` + 新的资源 + 新的缓存标志。

### 缓存的类型和网络拓扑

根据缓存的使用对象可以将缓存分为两种：私有缓存和公有缓存。

私有缓存仅供个人使用，它不需要占有很大的存储空间。大多数浏览器都会将常用的文档缓存到内存或者磁盘中。

公有缓存则是供多用户使用的共享缓存，被称为是缓存代理服务器，或者代理缓存。它可以从其本地读取缓存内容，也可以代表客户端像服务端请求。

## http报文

### 状态码

HTTP 状态码用于客户端了解请求处理的结果，总共被分为五类。

| 分类 | 范围 | 说明 |
|------|------|------|
| 信息类状态码 | 100 ~ 199 | 请求已接收，继续处理 |
| 成功状态码 | 200 ~ 299 | 请求已成功处理 |
| 重定向状态码 | 300 ~ 399 | 需要进一步操作以完成请求 |
| 客户端错误状态码 | 400 ~ 499 | 请求包含错误，服务器无法处理 |
| 服务端错误状态码 | 500 ~ 599 | 服务器处理请求时发生错误 |

- 信息类状态码（100 ~ 199）

   | 状态码 | 名称 | 说明 |
   |--------|------|------|
   | 100 | Continue | 请求的初始部分已接收，客户端可继续发送请求 |
   | 101 | Switching Protocols | 服务器根据客户端的指定，将协议切换为 Upgrade 首部所列的协议 |

- 成功状态码（200 ~ 299）

   | 状态码 | 名称 | 说明 |
   |--------|------|------|
   | 200 | OK | 请求没有问题，响应主体部分包含了服务端所需要的资源 |

- 重定向状态码（300 ~ 399）

   | 状态码 | 名称 | 说明 |
   |--------|------|------|
   | 300 | Multiple Choices | 客户端请求实际指向多个资源，返回此状态码时会带有一个资源选项列表 |
   | 301 | Moved Permanently | 资源被永久移动，响应的 Location 可以包含资源现在所处的 URL |
   | 302 | Found | 资源被临时移动，客户端应使用 Location 给定的临时 URL 来定位资源，将来请求依旧使用老的 URL |
   | 303 | See Other | 告知客户端应使用另一个 URL 来访问资源，新的 URL 位于响应的 Location 首部 |
   | 304 | Not Modified | 资源没有被修改，可以使用协商缓存中临时缓存的资源 |
   | 305 | Use Proxy | 说明必须通过代理来访问资源，代理的 URL 由响应的 Location 首部给出 |

- 客户端错误状态码（400 ~ 499）

   | 状态码 | 名称 | 说明 |
   |--------|------|------|
   | 400 | Bad Request | 告知客户端它发送了一个错误的请求 |
   | 401 | Unauthorized | 未授权，告诉客户端需要先认证才能获取资源的访问权限 |
   | 402 | Payment Required | 此状态码暂未使用，保留供将来使用 |
   | 403 | Forbidden | 请求被拒绝，服务端可在响应主体部分说明拒绝原因，但通常用于服务端不想说明拒绝原因时 |
   | 405 | Method Not Allowed | 请求中带有该 URL 不支持的方法时返回，应在响应首部 Allow 字段中说明支持的 HTTP 方法 |

- 服务端错误状态码（500 ~ 599）

   | 状态码  | 名称 | 说明 |
   |--------|------|------|
   | 500    | Internal Server Error | 服务器内部错误，无法正确处理请求 |
   | 501    | Not Implemented | 客户端发起的请求超出服务器能力范围（如使用了服务器不支持的请求方法） |
